# WearEngine Bridge

[English](README.md) | Русский

Небольшой LSPosed/Vector-модуль для разработки приложений Huawei Lite Wearable.

## Какую проблему решает

Переподписанная сборка DevEco Assistant или собственный клиент WearEngine могут
не получить список подключённых часов и вернуть ошибку:

```text
Scope unauthorized
```

Huawei Health проверяет доступ вызывающего приложения к WearEngine. Если изменить
клиент и подписать его своим ключом, эта проверка может отклонить запрос — даже
когда часы уже сопряжены с Health.

WearEngine Bridge работает внутри Huawei Health и разрешает запросы к scope
управления устройствами WearEngine независимо от package ID и сертификата клиента.
Это позволяет использовать изменённый DevEco Assistant или собственный клиент
в процессе разработки приложений для часов.

Модуль решает именно эту проблему доступа. Он не устанавливает HAP самостоятельно:
передача и установка приложения остаются задачей клиента. Проверки на часах и
отдельное согласие пользователя в Health не меняются.

## Совместимость

| Компонент | Состояние |
| --- | --- |
| Базовая версия Huawei Health | 17.0.8.300, versionCode 1700008300; на остальных модуль пытается работать, но они не проверены |
| Устройство, на котором проверяли | Android 15, Magisk 31, Vector/LSPosed |
| Framework API | Legacy Xposed API 82 |
| Минимальный Android в manifest | API 26; не является заявлением о тестировании всех версий |
| Версия модуля | 0.1, versionCode 1 |

Пользователь подтвердил работу перехвата в предварительной сборке после
отключения Frida. В 0.1 сохранено scope-решение, убран heartbeat, добавлен выбор
диагностики и заменён запрет по версии Health предупреждением. Разработчик подтвердил успешную сборку, установку и работу подписанного APK 0.1
на своём телефоне. Другие версии Health пока не проверены.
Установка HAP на часы отдельно не проверена.

Публичная нумерация начинается с versionName 0.1 и versionCode 1.
Если установлена предварительная сборка с более высоким versionCode,
перед установкой 0.1 нужно удалить прежний APK модуля. Health удалять не нужно.

На другой версии Health модуль пишет `WARN untested Health` и продолжает попытку
установки hook. Версия сама по себе не запрещает работу. Проверяются точное имя
класса, аргументы метода, boolean-результат и отсутствие static. При несовпадении
контракта scope-проверка остаётся штатной, причина записывается в журнал.
Совпадение сигнатуры не гарантирует совместимость внутренней логики другой версии.

## Установка

1. Установить **подписанный** APK обычным установщиком Android.
2. В Vector/LSPosed включить WearEngine Bridge и выбрать только
   **Huawei Health / com.huawei.health**. Клиентские приложения выбирать не нужно.
3. Health должен быть исключён из принудительного Magisk DenyList.
4. Через настройки Android остановить Health, затем открыть Health и DevEco
   или свой клиент. Проверить получение устройств.

У модуля нет Activity, значка запуска, сервиса или дополнительных разрешений.
Чтобы обновить его поверх предыдущего APK, нужна та же подпись.
Для проверки автономной работы отключить Frida и другие варианты этого обхода.
Откат: отключить модуль и перезапустить Health; данные Health очищать не нужно.

## Как устроен перехват

В процессах `com.huawei.health:DaemonService` и `com.huawei.health:PhoneService`
отслеживается загрузка класса `com.huawei.wearengine.scope.ScopeManager`.
Для каждой отдельной Java Class устанавливается hook метода:

```java
boolean checkScopeAvailability(String scope, int clientPid, int clientUid, String channel)
```

При `scope = com.huawei.hiwear.devicemanager` и `channel = wearEngine` он
возвращает `true`, не вызывая оригинал. Другие обращения выполняются штатно.
Это обход всего выбранного scope-gate, включая проверку сертификата и списка
допущенных возможностей, а не восстановление оригинальной подписи APK.
Отдельное согласие пользователя в Health не обходится. Проверки на часах
модуль не перехватывает.

Health загружает плагины через дополнительные ClassLoader. Одинаковое имя
класса у разных загрузчиков может обозначать разные Class. Поэтому реестр
устраняет повторы по идентичности Class, а наблюдатели продолжают работать
после первого успешного hook. Перехват действует на все экземпляры класса.
Используются события загрузки, без polling, таймеров и отложенных повторов.

| Файл | Назначение |
| --- | --- |
| `src/.../AccessPolicy.java` | Базовая версия Health для предупреждения, процессы и scope/channel |
| `src/.../ClassHookRegistry.java` | Учёт отдельных Class, защита от повторной установки |
| `src/.../WearEngineHook.java` | Bootstrap, наблюдение загрузчиков и hook |
| `assets/xposed_init` | Точка входа для framework |
| `res/values/arrays.xml` | Рекомендуемая область действия модуля |
| `tests/` | Проверки политики и реестра на JVM |

## Сборка

Нужны Python 3.9+, JDK с javac/jar, Android SDK Platform 35 и Build Tools 36.1.0.
Проверенная локальная среда: Windows, Python 3.11, JDK 8. Обычная сборка также
проверена на Ubuntu 24.04, Python 3.11, JDK 17. macOS не проверена.

Gradle не используется. В Android Studio можно открыть папку и запускать
`build.py` в терминале; это не Gradle-проект с задачей Assemble.

SDK/JDK задаются параметрами `--sdk` и `--jdk`. Также поддержаны стандартные
ANDROID_HOME / ANDROID_SDK_ROOT, JAVA_HOME и поиск javac в PATH. Скрипт не
печатает значения окружения. При настроенных SDK/JDK достаточно:

```sh
python build.py --fetch-api
```

Первый `--fetch-api` разрешает скачать закреплённый Xposed API 82 из
[репозитория API](https://api.xposed.info/de/robv/android/xposed/api/82/api-82.jar)
в игнорируемый `build/deps/`. SHA-256 проверяется перед использованием:
`f48c635f1c7469fdec0e00ad2ea0b7a6b2f5b55065784a35b7ca3a84615e8e25`.
Для офлайн-сборки можно передать `--xposed-api /path/to/api-82.jar`.
API используется только при компиляции и не упаковывается в APK,
согласно [инструкции Xposed](https://github.com/rovo89/XposedBridge/wiki/Using-the-Xposed-Framework-API).

Пример с явными путями (заменить на свои):

```sh
python build.py --sdk "PATH_TO_ANDROID_SDK" --jdk "PATH_TO_JDK" --fetch-api
```

Последовательность: javac → JVM-тесты → D8 → aapt2 → zipalign.
APK и JSON-отчёт появляются в `dist/<время>-normal/`, промежуточные результаты
и журналы — в `build/`. Старые сборки не удаляются и не перезаписываются.
Пакет Huawei Health для компиляции не нужен.

По умолчанию APK **не подписан и не готов к установке**. Для локальной подписи
предусмотрены параметры с путями к внешним файлам:

```sh
python build.py --fetch-api --keystore "PATH_TO_KEY.p12" --ks-alias "ALIAS" --ks-pass-file "PATH_TO_PASSWORD_FILE"
```

Пароль передаётся apksigner ссылкой `file:`, Python его не читает.
Ключи и пароли не хранятся в проекте. `--key-pass-file` нужен только для отдельного
пароля ключа; при одинаковом пароле PKCS12 повторно указывать тот же файл не нужно.
`--previous-apk PATH` дополнительно проверяет совпадение сертификата обновления.
Подпись v2/v3, v1 отключена явно; minSdk 26 покрывается v2.
Команд установки, доступа к телефону, публикации или загрузки релиза нет.

## Логи и проверка

Обычная сборка пишет `READY` для установленного hook и сообщения об ошибках.
Heartbeat отсутствует. Для подробных загрузчиков и каждого вызова:

```sh
python build.py --fetch-api --diagnostic
```

Сообщения одновременно записываются в журнал модулей Vector/LSPosed и Android
Logcat. В виде уведомлений или внутри DevEco Assistant они не показываются.

**На телефоне:** открой менеджер Vector/LSPosed, перейди в раздел **Логи / Logs**
(название зависит от версии и языка) и ищи `WearEngineBridge` в журнале модулей.
Если поля поиска нет, экспортируй журнал и найди эту строку в сохранённом тексте.

**В Android Studio:** открой **View > Tool Windows > Logcat**, выбери подключённый
телефон и введи фильтр `tag:WearEngineBridge`. Включи отображение уровня **Info**.
Убери `package:mine` и ограничения на процесс модуля или DevEco Assistant:
сообщения поступают из процессов Huawei Health `:DaemonService` и `:PhoneService`.

Чтобы заново увидеть установку hook, начни просмотр журнала, принудительно останови
Huawei Health через настройки Android, затем открой Health и клиент WearEngine
и повтори запрос. Сообщения появляются по событиям; периодического heartbeat нет.
`READY`, `CLASS_INACTIVE` и `CLASS_HOOK_FAILED` есть и в обычной сборке.
Диагностическая сборка нужна для подробностей о загрузчиках и отдельных вызовах.

Диагностическая сборка содержит CLASS_FOUND, CALL/RETURN, process, PID и classId.
READY подтверждает установку hook; проверять нужно ещё успешный результат
getDevices в клиенте. Диагностические и обычные APK имеют один package/code:
при переключении вариантов нужна одинаковая подпись и перезапуск Health.

Сборщик запускает 18 проверок AccessPolicy и 14 проверок реестра Class
(разные JVM-загрузчики, ранняя/поздняя загрузка, конкурентная регистрация).
Дополнительно проверяются manifest, ZIP/CRC, DEX, отсутствие встроенного
framework/native-библиотек/heartbeat, вариант логирования и выравнивание.
При подписи проверяются сертификат и подпись APK. JVM-тесты не заменяют
проверку ART/framework на телефоне.

## Границы репозитория и лицензия

В проект входят только исходники модуля, тесты, сборка и документация.
APK Huawei, декомпиляция, личные журналы и старый standalone Zygisk-движок
не требуются. `build/`, `dist/`, IDE-файлы и ключи исключены через `.gitignore`.
Публикацию релизов организует владелец проекта.

MIT — см. [LICENSE](LICENSE). Xposed API — внешняя compile-only зависимость;
его бинарник не включается в исходники или APK модуля.

## Продолжение работы на другом компьютере

Скопировать или клонировать репозиторий, установить Python, JDK и Android SDK
с версиями компонентов из раздела «Сборка». Затем выполнить:

```sh
python build.py --sdk "PATH_TO_ANDROID_SDK" --jdk "PATH_TO_JDK" --fetch-api
```

В коде нет путей с компьютера автора. `PATH_TO_*` в примерах нужно заменить
своими путями. Кеш Xposed API загрузится заново; переносить build/ и dist/ не нужно.
Для компиляции и тестов ключ подписи не требуется. Для устанавливаемого APK
нужно отдельно указать внешний ключ и файл пароля, как описано выше.
Сохраняйте один ключ для последовательных обновлений модуля.
